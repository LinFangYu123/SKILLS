# Grill（连环拷问，打磨方案）

通过**多轮追问**与用户对齐认知，直到方案中的每个决策都显式确定、
没有留下任何隐含假设。默认**只拷问、不产出文档**；仅当用户明确要求
（如「生成文档」「写 ADR」「记录下来」）时，才进入文档模式。

---

## 核心流程：设计树 + 轮次追问

把对话建模为一棵**设计树（design tree）**：每个决策会分叉出挂在它下面的
子决策。整场会话就是在逐步填满这棵树。

### 轮次（rounds）与前沿（frontier）

**前沿**是所有「前置决策已敲定」的问题——即现在就能问、不需要先猜
其他答案的问题。每轮把**整个前沿**一次问完：

1. 给每个问题编号
2. 每个问题都给出你的**推荐答案**
3. 然后停下，等用户回答后再进入下一轮

每轮的回答会重塑设计树：已敲定的决策把前沿向外推，解锁原本被阻塞的
问题。重新计算前沿，开始下一轮。

> ⚠️ 答案依赖本轮其他未决问题的问题，属于**后续轮次**，不要提前问。

轮次格式：

```
❓ **Q1** - **<问题标题>**：<问题正文，可多段，可含多个选项>

➡️ <你的推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文>

➡️ <你的推荐答案>
```

### 事实自己查，决策问用户

- **找事实是你的职责**：前沿问题若需要环境中的事实（文件系统、代码库、
  工具调用等），派 sub-agent 去查，不要反问用户。
- **不要阻塞**：探索进行中算「未决前置」——只有下游依赖它的问题需要
  等待结果，前沿的其余问题照常本轮提出。
- **决策是用户的**：每个决策都交给用户拍板，并等待回答。

### 收尾条件

前沿为空 = 会话结束：设计树每个分支都走过一遍，没有留下任何默默
假设的东西。

**在用户确认已达成共识之前，不要基于方案采取任何行动。**

## 文档模式（仅在被明确要求时启用）

只有用户明确要求生成文档时，才启用本节。默认情况下，即使讨论中
沉淀了术语和决策，也**不要**写任何文件。

用户开启文档模式后，在拷问进行的同时按以下纪律实时沉淀：

### 文件结构（惰性创建）

```
/
├── CONTEXT.md            ← 词汇表（且仅是词汇表）
└── docs/adr/             ← 架构决策记录
    ├── 0001-slug.md
    └── 0002-slug.md
```

- 没有 `CONTEXT.md`：**第一个术语敲定时**才创建
- 没有 `docs/adr/`：**第一个 ADR 需要记录时**才创建
- 若根目录存在 `CONTEXT-MAP.md`，表示多上下文仓库，按 map 中的指引
  定位各上下文自己的 `CONTEXT.md` 与 `docs/adr/`

### 会话中的纪律

- **对照词汇表挑战**：用户用词与 `CONTEXT.md` 现有定义冲突时立即指出
  （「词汇表里『取消』定义为 X，但你刚才的意思是 Y，到底是哪个？」）
- **磨尖模糊语言**：用户用了含糊或一词多义的术语，提议一个精确的
  规范术语（「你说的『账户』是指 Customer 还是 User？这是两个东西」）
- **具体场景压测**：讨论领域关系时，构造戳边界、探极端的具体场景，
  逼用户对概念边界表态
- **与代码交叉验证**：用户陈述某处的工作方式时，检查代码是否一致；
  发现矛盾就摆出来问清楚
- **术语实时入表**：一个术语敲定，**立即**更新 `CONTEXT.md`，不要攒批。
  `CONTEXT.md` 不含任何实现细节——它是词汇表，不是 spec 或草稿本
- **ADR 克制地记**：满足全部三个条件才提议写 ADR（见下）

### ADR 三条件（缺一不记）

1. **难以逆转**：以后改主意的代价是实质性的
2. **没有上下文会令人费解**：未来的读者会问「为什么当初这么做？」
3. **真实权衡的结果**：确实存在其他选项，且你是基于具体理由选了这个

格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)，词汇表格式见
[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。
