# Explain Clearly（讲到一次就懂）

## 讲解骨架

四步按序走完，缺哪步听众就在哪步掉队。

1. **最小完整答案先行**。用一两句给出「它是什么 / 发生了什么」的完整回答，不铺垫背景、不预告「接下来我会讲三点」。听众读完这两句就该能答上自己的问题；后面全是给这个答案补机制。
2. **一个类比**。把新东西挂到听众已有的概念上（池子由受众决定，见下），紧接着说明它在哪不成立。类比负责建立直觉，代价是必然失真，所以失效边界和类比本身一样重要。
3. **机制**。它实际怎么工作。到这一层才引入新术语，每引入一个就立刻给听众语言里的等价说法及其差异（如对 C 听众：「Python 的 dict 像手写查找表，但迭代是插入序，不是 key 排序序」）。
4. **对你的影响**。这个机制会改变哪个决定、哪段代码、哪个预期。听众不关心它「设计优雅」，关心「所以我该怎么做」。

第 4 步的判据：**如果这条换到别的话题也成立，说明它是空话，删掉**（「要注意边界情况」是典型空话）。

## 任务分支

### 概念与机制

走完四步骨架。若主题属于听众没接触过的领域（金融、生物、法律），在第 1 步前先补一句「这个领域的人在解决什么问题」，用听众世界的等价问题说明——缺了这句，后面的机制无处挂靠。

### 报错与堆栈

1. 先用一句人话翻译它在抱怨什么，不要照抄英文原文。
2. 从堆栈里指出**真正的肇事帧**——通常是第一个属于听众自己代码的帧，而不是库的最内层。从最深处读起只会迷路。
3. 根因：为什么这行会触发它，而不是只复述报错文本。
4. 修法：给出可粘贴的最小修改，并标明改了哪几处。

### 代码与设计

先给这段代码的**职责**（它保证什么、谁调用它），再走机制。回答「为什么这么写」时，把当时可能的替代方案摆出来、说明为什么没选——听众要的是决策依据，不是复述代码。不逐行翻译语法，只讲在听众语言里没有对应写法的那些行。

### 英文术语与缩写

一行定义 + 一个类比 + 该术语出现的语境（谁在什么场合说它）。术语在中文技术语境有惯用译法时一并给出。

### 别人的文档与设计

1. 先定位对方在解决什么问题、假设了什么前提。对方的语境不是听众的语境。
2. 补上对方省略的上下文——对方省略它，是因为在他的环境里显然，在听众这不显然。
3. 用听众的语言重述一遍核心主张，再说明它的适用条件：什么情况下这条建议不成立。
4. 区分**作者的主张**和**作者的证据**。很多文档把两者混在一起，只有证据能支撑主张。

判据：能指出至少一条该文档的前提在听众这里不成立，或明确说清它在什么条件下成立。

### 数学 / 金融 / 算法

1. 先给数量级直觉：这个数是大是小，波动多少算正常。没有量感，公式只是一堆符号。
2. 公式先讲它想表达的关系，再讲符号含义，最后才讲推导。
3. 用听众语言的等价物算一遍具体数字（100 万本金、5% 利差 = 5 万），不用抽象百分比讲完就走。
4. 相关与因果分开说：两个量同时变化，不等于其中一个导致了另一个。

判据：听众能用「大概多少」的口头描述替代公式复述一遍。

## 铁律

- 每个技术名词首次出现时**立刻**给听众语言里的等价说法。
- 类比之后立刻标注失效边界。只给类比的解释，会在听众拿它外推时出错。
- 结论先行。最小完整答案一两句，听众追问再往下加层。
- 100% 准确的讲法会把听众甩下时，选 80% 准确但讲得下去的讲法，并标明在哪里做了简化。
- 技术术语在技术受众之间保留英文原文，不强行翻译。
- 讲得简单不等于讲得幼稚。听众是不是专家，取决于领域——在自己领域里被当外行对待，是冒犯。
- 听众的既有语言是**桥梁不是内容**：拿 C 讲 Python 时，讲的是 Python，不是 C。

## 完成判据

- 听众能用自己的话一句话复述核心机制，且这句话不含未定义的术语。
- 每个新术语都配了等价说法；每个类比都标了失效边界。
- 结尾那条「对你的影响」不能被替换到别的话题上。
- 跨受众交付时（如「讲给我老板听」），说明里不含听众语言里不存在的概念，除非当场定义了它。
