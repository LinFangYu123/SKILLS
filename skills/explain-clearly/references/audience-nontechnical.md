# 受众：非技术听众（管理 / 业务 / 家人）

读者画像：不在工程岗位，不读代码，关心的是**影响、成本、时间、风险、要做什么决定**。
**触发表述：**「讲给我妈/我老板听」「非技术」「业务方」「不用术语」。

## 唯一目标

让听众能回答两个问题：

1. 这对我意味着什么？
2. 需要我做什么决定，或者需要我知道什么风险？

答不上这两个，解释就是失败的——哪怕技术上完全正确。

## 规则

- **不出现技术名词**，包括「服务器」「API」「数据库」「前端」「部署」。需要一个不可绕开的概念时，当场用生活类比命名它，此后沿用同一个名字，不再换词。
- 开头先给**影响**，不是定义。顺序是：会发生什么 → 谁受影响 → 要花多少时间或钱 → 你要决定什么 → 风险是什么。
- 时间给区间不给点估（「一到两周」而非「十天」），并说明区间为什么宽。
- 数字换成具体量级（「大概一个月的营收」而非「约 12.7%」），同时给出原始数字备查。
- 有不确定性就直接说，并说明它会不会随时间收敛。管理者最怕的是「听起来很确定，后来发现不是」。
- 需要决策时，给**明确推荐 + 一个备选**，各自代价写清。不要抛一堆选项让人挑——那是把决策成本转移回去。

## 类比池

生活场景优先，选听众日常熟悉的那一类：

| 场景 | 可用类比 |
| --- | --- |
| 排队与容量 | 超市收银台、停车位、医院挂号 |
| 存储与积压 | 仓库、衣柜、待办便签 |
| 分发与同步 | 快递、抄送多份文件、流水席上菜 |
| 权限与安全 | 门禁卡、保险箱、钥匙保管 |
| 成本与折旧 | 房租、水电、一次性投入 vs 每月开销 |
| 风险与备份 | 保险、备用钥匙、应急基金 |

## 语气

- 尊重，平视。对方在自己的专业领域（预算、组织、市场）比讲解者懂得多。
- 说「我们看下这个选择」，不说「简单地讲」「通俗地说」——后者暗示对方层次低。
- 不用「其实很简单」，这句话对听众是压力不是安慰。
- 对方追问技术细节时，先给一个能支撑决策的层次，再问要不要往下一层走。

## 完成判据

- 全文没有听众语言里不存在的概念（除非当场定义了它）。
- 听众能复述「这对我意味着什么」和「我要决定什么」。
- 每条风险都配了它的应对方式或观察信号。
