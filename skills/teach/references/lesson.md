# 讲义（lessons/）

讲义是本技能的主要产出：每节一个自包含 HTML 文件，`lessons/NNNN-<dash-case-name>.html`，编号递增。

用户会反复回来翻它，所以它必须**好看**——干净、可读的排版，印刷出来也体面。目标是 Tufte 那种克制：单栏、宽留白、少色彩、信息密度高而不拥挤。

## 一节课的纪律

- **短，且当次就能读完做完。** 学习者的工作记忆很小。宁可拆成三节，也不要在一节里塞三个主题。
- **一个可拿走的胜利。** 每节课结束时用户必须多出一样**能做的事**，而不只是多知道一些事。
- **紧挂使命。** 讲义开头就写清它服务于 `PROGRESS.md` 里的哪个里程碑。
- **落在最近发展区。** 太浅是浪费时间，太深是挫败。判据：用户读的时候会偶尔卡住，但不需要外部帮助就能过。
- **每节推荐一个一手来源。** 取自 `RESOURCES.md`，用链接指向它，让用户能自己往下走。
- **每节都要提醒"可以追问老师"。** 你是他的老师，任何不清楚的地方都可以问。

## HTML 骨架

`assets/style.css` 和 `assets/quiz.js` 已经由 `scripts/scaffold_workspace.py` 落好，直接引用相对路径：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>0003 · 悲观锁与乐观锁</title>
<link rel="stylesheet" href="../assets/style.css">
</head>
<body>
<article>

<header class="lesson-head">
  <p class="eyebrow">第 3 节 · 里程碑 2：能给出正确的并发方案</p>
  <h1>悲观锁与乐观锁</h1>
  <p class="lede">学完这节，你能看着一段并发写入代码，判断该选哪种锁并说出理由。</p>
</header>

<!-- 正文，见下节结构 -->

<footer class="lesson-foot">
  <p>一手来源：<a href="...">{来源标题}</a></p>
  <p>相关：<a href="0002-....html">第 2 节 · 事务隔离级别</a> · <a href="../reference/glossary.html">术语表</a></p>
  <p>没懂的地方直接问我——我是你的老师，追问不用客气。</p>
</footer>

</article>
<script src="../assets/quiz.js"></script>
</body>
</html>
```

`lang` 跟用户语言走。`<title>` 里带上编号，方便翻标签页。

## 正文结构

按这个顺序写，它是"理解 → 模仿 → 独立"的支架：

1. **`.lede`**：一句话说清学完能做什么。不写"本节介绍……"，写可观察的能力。
2. **核心概念**：一次只讲一个概念。**先平实定义，再绑到具体场景**（"一般情况下它是 X；在我们这个 case 里拿它干 Y"），再讲它怎么工作、为什么这么设计、边界在哪。需要图就按下面的增量图规则来。
3. **完整示范（worked example）**：一个从头到尾做对的例子，每一步都写清**为什么这么做**，而不是只有结果。这是脚手架的第一级。
4. **渐撤练习**：给一个留了一半的同类问题，让用户补完。这是第二级。
5. **独立练习**：一个只给要求、不给步骤的问题。这是第三级，通常紧接测验。
6. **自测**（见下节）。
7. **`.lesson-foot`**：一手来源、相关讲义、术语表链接、"可以追问"。

写完自查每条：**这一句是在讲知识，还是在帮用户建立技能？** 只有功能列表、没有机制解释的内容是参考资料，放到 `reference/`，不要塞进讲义。

## 视觉规范

`assets/style.css` 已经实现了下列约定，写正文时用它的类名与语义标签即可：

| 用途 | 写法 |
| --- | --- |
| 提示、陷阱、旁注 | `<aside class="note">`、`<aside class="warn">`、`<aside class="why">` |
| 代码 | `<pre><code>`；行内 `<code>` |
| 对照 | `<table>`——两种以上方案对比优先用表，不用散文 |
| 流程图/结构 | 内联 `<svg>`（包在 `<figure>` 里配 `<figcaption>`），或 `<pre class="ascii">` 里的 ASCII 图 |
| 关键定义 | `<dl><dt>术语</dt><dd>定义</dd></dl>` |
| 折叠答案 | `<details><summary>看答案</summary>…</details>` |

- **两种以上方案比较、参数对照、正反例对照，一律用表格**，不要写成一串"首先……其次……"。
- 需要外部资源时只引 `RESOURCES.md` 里的来源，并在正文里以链接形式标注出处，让每个断言都能被追溯。
- **图一律内联 SVG 或 ASCII**，不要用 mermaid / 图表 CDN：讲义必须能离线打开、能打印。
- 颜色只用样式表给的变量。**不要引入新的 CDN、字体或 JS 库。**

## 练习与测验

自测区用 `assets/quiz.js` 驱动：写 `<ol class="quiz">`，每题一个 `<li data-answer="b">`，选项是 `<ul class="opts"><li data-key="a">`。答对答错由脚本标色、揭示 `.why`，并给出一次小结。结构示例：

```html
<ol class="quiz">
  <li data-answer="b">
    <p class="stem">写冲突密集的计数器更新，选哪种锁？</p>
    <ul class="opts">
      <li data-key="a">乐观锁</li>
      <li data-key="b">悲观锁</li>
      <li data-key="c">不用锁</li>
      <li data-key="d">读锁</li>
    </ul>
    <p class="why">冲突率高时乐观锁的重试代价按冲突率上升，反而更慢。</p>
  </li>
</ol>
```

**零提示是硬约束**——每道题只能被真正懂的人答对：

1. 选项描述不得泄露正确性。反例：`悲观锁 —— 适合写冲突高的场景`；正例：`悲观锁 —— 写入前先持有排他锁`。
2. 任何选项都不加"(推荐)"。
3. **打乱正确项位置**，不要总在首位。
4. 题干问行为/用途/输出，不暗示答案。反例"`error()` 向哪个流输出？"；正例"`error()` 的输出去了哪里？"。
5. 错误选项必须是该领域**真实存在的概念**，而且是常见误解——瞎编的干扰项会让题目变成猜谜。

题量与难度按场景调（写在讲义里的是自测，通常 3-5 题）：诊断用 40% 易 / 40% 中 / 20% 难；刷弱项用 30% 中 / 70% 难；复习则各档均匀。

**重考弱项概念时换语境**：不要重问原题，换个角度考同一个底层知识。比如用户混了"400 vs 422"，就编一个新场景让他选。

课后对话里的正式测验是 **4 题、每题 4 个选项**，判分后按 [../SKILL.md](../SKILL.md) 分支 2 第 6 步更新 `mastery/` 与 `PROGRESS.md`。

## assets 复用规则

**复用是默认，不是例外。** 写讲义前先读 `assets/`，能用的组件直接用。

需要新组件时（新的练习控件、图示器、对照表样式）：

1. 写成 `assets/` 里的独立文件（CSS 追加到 `assets/style.css`，JS 新建 `assets/<name>.js`）。
2. 讲义里链接它，**绝不内联**一段将来的讲义会重复的代码。
3. 首次创建一个新工作区时，`assets/style.css` 与 `assets/quiz.js` 由脚手架脚本落地；此后随着工作区长大，组件库也应该长。
