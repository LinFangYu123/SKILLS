# ADR 格式

ADR 存放在 `docs/adr/`，按序号递增命名：`0001-slug.md`、`0002-slug.md`……

`docs/adr/` 目录惰性创建：只在需要记录第一个 ADR 时建立。

编号规则：扫描 `docs/adr/` 中已有的最大编号，加一。

## 模板

```md
# {决策的简短标题}

{1–3 句话：背景是什么、我们决定了什么、为什么。}
```

就这些。一个 ADR 可以只是一段话。价值在于记录**做了这个决策**以及
**为什么**，而不在于填满各个章节。

## 可选章节

只在真正增加价值时才加，多数 ADR 不需要：

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：
  决策会被重新审视时有用
- **Considered Options**：被否决的备选方案值得记住时才写
- **Consequences**：有不明显的下游影响需要指出时才写

## 什么时候值得写 ADR

必须同时满足三个条件：

1. **难以逆转**：以后改主意的代价是实质性的
2. **没有上下文会令人费解**：未来的读者看着代码会问「为什么当初这么做？」
3. **真实权衡的结果**：确实存在其他选项，且你是基于具体理由选了这个

容易逆转的决策不要记——直接改就行。不令人意外的决策没人会问为什么。
没有真实备选项的决策，记录下来也只是「我们做了显然的选择」。

### 典型 qualifies 的例子

- **架构形态**：「我们用 monorepo」「写模型事件溯源，读模型投影进 Postgres」
- **上下文间的集成模式**：「Ordering 与 Billing 通过领域事件通信，不用同步 HTTP」
- **有锁定效应的技术选型**：数据库、消息总线、认证服务商、部署目标。
  不是每个库都记，只记换掉要花一个季度的那些
- **边界与范围决策**：「Customer 数据归 Customer 上下文所有，其他上下文
  只通过 ID 引用」——明确的「不做」和「做」同样有价值
- **对显然路径的有意偏离**：「因为 X，我们手写 SQL 而不用 ORM」。
  这类记录能阻止下一个工程师把深思熟虑的设计当 bug「修掉」
- **代码里看不出来的约束**：「因为合规要求不能上 AWS」「响应时间必须
  200ms 以内，因为合作方 API 合同」
- **否决理由不明显的备选方案**：考虑过 GraphQL 但出于微妙的原因选了 REST
  就记下来，否则半年后还会有人再提 GraphQL
