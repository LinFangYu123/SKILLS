# 受众：Web / JS-TS 工程师

读者画像：熟悉 JavaScript / TypeScript、npm、浏览器或 Node 运行时、React 等框架生态，
但很可能没有系统学过内存管理、指针、编译链接、二进制协议。**触发表述：**
「讲给前端同事」「解释给会 JS 的人」「给做 Web 的看」。

## 语气校准

- 可直接使用：闭包、Promise / async-await、事件循环、原型链、npm 依赖、打包、DOM、`ArrayBuffer`。
- 不要把「函数是一等公民」「回调」当作需要解释的概念——他们比 C 程序员熟得多。
- 他们把 **V8 的分代 GC**（新生代 / 老生代）当作常识，讲内存话题时可以直接引用。
- 技术术语保留英文原文。

## 类比池

| 新概念 | 挂靠到 | 必须同时说明的差异 |
| --- | --- | --- |
| 指针 | JS 的对象引用，但**可以解引用和做算术** | JS 引用无法取地址、不能偏移，也不存在悬垂问题 |
| `malloc` / `free` | 无对应物。最接近的是「手动管理 `ArrayBuffer` 的生命周期」 | 真正区别是**谁负责释放**：C 里是人，JS 里是 GC |
| 栈与堆 | 调用栈存帧、堆存对象 | C 的栈上可以放整个结构体，JS 的栈上只有原始值和引用 |
| 内存泄漏 | 已经不用的引用仍被持有（detached DOM、未移除的监听器） | 在 C 里泄漏是「忘了 free」，在 JS 里是「引用链没断」——**机制不同，症状相同** |
| 编译 / 静态链接的二进制 | 打包产物（bundle） | C 编译到机器码、由 OS 直接加载；bundle 编译到中间格式、由运行时解释或 JIT |
| 动态链接 | `node_modules` 的依赖解析与提升 | C 在加载期由链接器解析符号，失败是**硬错误**；JS 的解析失败常在运行时才炸 |
| 进程与线程 | Web Worker / Node worker_threads / cluster | Worker 之间不共享内存（除非 `SharedArrayBuffer`），C 的线程默认共享整个地址空间 |
| 锁与数据竞争 | JS 主线程单线程，所以**默认没有这个问题**；`SharedArrayBuffer` + `Atomics` 才引入真并发 | 「没有锁」不是免费的，代价是用不了多核 |
| 字节序 | `DataView` 的 `getUint32(offset, littleEndian)` 参数 | 前端只在跨二进制协议时遇到，C 里它影响结构体内存布局 |
| 二进制协议 | `ArrayBuffer` + `DataView` 手工解析 | C 用结构体强转直接读，代价是对齐和字节序的平台差异 |
| Python 的 GIL | 类比 Node 的单线程事件循环 | GIL 是**同一时刻只有一个线程执行字节码**；I/O 等待时会释放，CPU 密集任务不会 |
| Python 装饰器 | 高阶函数 / HOC（`withAuth(Component)`） | 机制几乎同构，不存在 JS 那种 `this` 绑定陷阱 |
| Python 的 venv | 每个项目独立的 `node_modules` | venv 换的是**解释器自己的搜索路径**，不改全局 `PATH`；`node_modules` 是目录级解析 |
| GC 暂停 | 无直接对应物，JS 也有（V8 的 stop-the-world） | 讲 C 时反过来用：C 的 `free` 延迟可预测，GC 的暂停不可预测 |
| 无 GC 的世界 | 关掉 GC 用 `FinalizationRegistry` 都不够；真正的对照是 WASM 里手动管内存 | 这是 Web 工程师最缺的一块直觉，值得多花两句 |

## 失效边界

- 用 JS 的「引用」类比 C 的「指针」在**解引用和算术**这两点上立刻失效，讲到 `p+1`、`*p`、数组退化时必须明确说「JS 没有这个东西」。
- 不要把「事件循环」当成并发的通用模型：C 的线程是抢占式调度，回调式并发是协作式，两者的竞态条件完全不同。
